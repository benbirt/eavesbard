# E1 — Playing from sounds.tabletopaudio.com

**Status:** passed on Android Chrome, locally and over Cast. Desktop Chrome over Cast not yet tested.

## What was tried

The E1 test page on the deployed site (https://benbirt.github.io/eavesbard/) plays tracks straight from `https://sounds.tabletopaudio.com/<file>.mp3` through plain audio elements with no `crossOrigin` attribute.

## Results

**Audio host behaviour (curl, 2026-10-09)**
- No `Origin` header: 206, `audio/mp3`, range requests supported, whatever the `Referer` or user agent.
- Any `Origin` other than `https://tabletopaudio.com`: 403 AccessDenied.

**Local playback, headless Chromium on localhost (2026-10-09)**
- Audio requests carried no `Origin` header and got 206 `audio/mp3`.
- `playing` fired; seeking to 20 s before the end worked; `ended` fired.
- No page errors.

**Local playback, phone with Bluetooth headphones, deployed site (2026-10-09)**
- Played audibly; the event log showed `ended` after seeking near the end.

**Cast, Android Chrome, deployed site (2026-10-09)**
- At first the Cast SDK loaded and reported itself available, but its cast state stayed `NO_DEVICES_AVAILABLE` on a network with Cast devices, so no Cast icon appeared.
- Cause: Chrome lacked an Android permission needed for discovery. Once it was granted, the device was found, the Default Media Receiver played the track from sounds.tabletopaudio.com, and seeking and the track-end event worked.
- Web pages can't read that permission, so the page now shows a hint (Android: Nearby devices; macOS: Local Network) when no devices are found after a few seconds.

**Cast, desktop Chrome:** not yet tested.

## Decision

Streaming straight from Tabletop Audio's host works for both adapters, so the hosting plan holds and E3's fallbacks aren't needed. Desktop Chrome over Cast still needs a confirming run on the real host laptop.
