# E9 — Local scene classifiers

**Status:** first round done offline (2026-10-10). Best: the current embedding classifier blended with a small instruction LLM, 70–74% on the held-out set against 63% for the classifier alone. Built into the app with Gemma 3 4B (DESIGN.md 7.5).

## Test sets

- **DEV** (`src/eval/scenarios.ts`, 17 scenes): the scenes the current classifier was tuned on. Used only to choose settings and blend weights.
- **TEST** (`src/eval/test-set.ts`, 108 scenes, held out): messy, Whisper-style transcript lines 15 s apart, plus typed opening descriptions. Each scene lists every acceptable setting and intensity.

| Category | Scenes | What it checks |
|---|---|---|
| opening | 30 | a typed opening description |
| setting | 24 | the setting changes during play |
| tense | 12 | danger without a fight |
| combat | 12 | a fight in progress |
| combat starts | 8 | a fight breaking out |
| combat ends | 12 | a fight just over |
| off-topic | 10 | table talk: rules, food, scheduling |

A result counts as right after the state machine's own rules (DESIGN.md 7.6): unknown or under-50%-confident results keep the current label, and an unknown opening setting becomes tavern. "Both" means setting and intensity are both right.

The harness is in `experiments/e9/`: Node, transformers.js 4.3.1 on the CPU (4 cores), importing the compiled sets from `bazel-bin`. Each script is a Bazel target: `bazel run //experiments/e9:<file>` (with `-` as `_`), listed in `experiments/e9/BUILD.bazel`.

## Results on TEST

| Method | Download | Time per check (CPU) | Setting | Intensity | Both |
|---|---|---|---|---|---|
| **L** — current: embeddings vs hand-written label descriptions | 34 MB | ms | 83% | 76% | 63% |
| **A** — vote of the 20 nearest tracks' tags | 34 MB | ms | 72% | 54% | 38% |
| **B** — zero-shot NLI, `MoritzLaurer/deberta-v3-xsmall-zeroshot-v1.1-all-33` | 87 MB | 0.1 s | 81% | 63% | 51% |
| **C** — Qwen3-1.7B (q4) | 1.4 GB* | 3 s | 81% | 74% | 61% |
| **C** — Gemma 3 4B (q4, text only) | 2.8 GB* | 7 s | 89% | 69% | 60% |
| L + B blend | 120 MB | 0.1 s | 85% | 75% | 66% |
| **L + Qwen3-1.7B blend** | 1.4 GB* | 3 s | 87% | 81% | **70%** |
| **L + Gemma 3 4B blend** | 2.8 GB* | 7 s | 92% | 81% | **74%** |

\* Browser q4f16 download for WebGPU. The CPU test used the q4 files, which are larger. On WebGPU each check should be well under the CPU times.

Blend weights were chosen on DEV and then scored once on TEST. Setting takes an even split of the two probability distributions; intensity takes 75% L and 25% LLM. L's off-topic rule is kept; its "unknown setting" rule is dropped because it costs openings.

L + Gemma 4B by category: opening 80%, setting 75%, tense 75%, combat 83%, combat starts 88%, combat ends 42%, off-topic 70%.

**Other models tried for B** (both, TEST): mobilebert-mnli 25%, distilbert-mnli 38%, nli-deberta-v3-xsmall 19%, nli-deberta-v3-small 19%.

**Other models tried for C**: SmolLM2-360M, Qwen2.5-0.5B, Qwen3-0.6B, Gemma 3 270M, Gemma 3 1B and Qwen2.5-1.5B all scored 2–31% both, near chance. Gemma 3 1B degrades badly when quantised for the CPU (q4 or 8-bit): it answers "Tavern" to "deep underground caverns", while at full precision it answers "Dungeon".

## How C works

- There is one forward pass per axis and no free generation.
- The prompt has the transcript (the last 150 words for the setting, 60 for the intensity) and the current scene ("keep that answer unless the transcript shows it has changed"). It lists the labels with one-line meanings and ends with "Answer:".
- The answer is read from the next-token probabilities of each label, adding the " dungeon" and " Dungeon" forms.
- Telling the model the current scene took Qwen3-1.7B from 47% to 61%.
- Reading the first answer token on its own, without prefilling "Answer:", gave near-random results: the models want to begin "From the given options…".

## Findings

- The approaches fail in different places. L is strong on combat and combat starting. The LLMs are strong on settings and tense scenes but slow to call combat. Blending fixes most of both.
- Combat ending is the weakest category for every method (25–58%).
- No method uses anything written per track, so the track index can be regenerated without anyone in the loop. L and B use a handful of one-line label definitions.
- Not compared with Claude Haiku on TEST: no API key was available. That reference number is still missing.

## In the browser

Tested in headless Chromium with SwiftShader (a CPU standing in for the GPU) through the app's own worker (`src/llm/llm-worker.ts`):
- **Gemma 3 4B** downloads, loads and answers. "Deep underground caverns" gives dungeon at over 99.9%. It took 74 s to download and prepare, and 293 s for the answer on SwiftShader; a real GPU is far faster.
- **SwiftShader has no 16-bit floats** (`shader-f16`), so the q4f16 files can't run on it. The worker checks for `shader-f16` and falls back to the q4 files (32-bit activations; about 3.2 GB for Gemma) on GPUs without it.
- **Qwen3 1.7B doesn't load:** onnx-community's q4f16 build is a single 1.4 GB file, and ONNX Runtime Web fails with `std::bad_alloc` creating the session. Gemma's builds keep the weights in separate `.onnx_data` files, which load. Re-saving Qwen's file that way (`experiments/e9/repack.py`) and serving the copy locally, the session loads and gets as far as SwiftShader's missing 16-bit floats. So Qwen3 1.7B would work from a hosted re-packed copy, for example a Hugging Face repo of ours, with `transformers.js_config.use_external_data_format` set in its `config.json`.

## Follow-up: fights not ending (real session, 2026-10-10)

In a real session with Gemma on a laptop GPU (about 1 s per check), "Roll for initiative" started combat, but "you killed the last enemy" and "Combat over" didn't end it:
- The embeddings read both as combat: they can't read negation.
- Gemma said calm both times, but had only 25% of the intensity vote.

Both checks are now in the DEV set. On the cached answers (`mix2.mjs`, `int-variants.mjs`):

| Change | TEST both | Combat ends |
|---|---|---|
| Blend as shipped | 74% | 42% |
| Gemma's answers softened (temperature 3) | 78% | 42% |
| Gemma not told the current scene, more weight in combat | 78% | 50% |
| Gemma told "before these lines the scene was …" | 77% | 0–33% |
| More LLM weight while in combat (without softening) | 73% | 33% |

Gemma is anchored by "keep that answer unless the transcript shows it has changed": mid-fight it calls looting and healing combat at 100%.

A direct question works better. While in combat, Gemma is also asked "is the fight still going on right now?" (ongoing or over; `fight-over.mjs`). Over all 26 scenes that start in combat:
- It never said over for a fight still going (0 of 9).
- It caught 7 of 17 endings, including both real ones (98% and 100%).
- The answers are almost always 0% or 100%, so the threshold hardly matters.

With softening and the fight-over question, TEST is 79% (combat ends 50%). Both are in the app.

## Round 2: on a real GPU (Apple M5, 2026-10-10)

The cloud container had 4 CPU cores and no GPU, so every Gemma run took 15–30 minutes and used the CPU build. The evaluation now runs in headless Chrome on a real GPU, through the app's own worker: `src/eval/llm-eval.ts` (built as `//src:eval_site`), driven by `browser-eval.mjs`, scored by `analyse.mjs`. A model loads from cache in seconds; a full run of 127 scenes with four prompt variants takes about 10 minutes.

**Gemma 3 4B was broken.** With 16-bit activations (the q4f16 files) every answer was NaN on the Apple GPU, almost certainly from activations overflowing 16-bit floats. The worker turned that into a uniform "all labels equally likely". So the real session's "Gemma: tavern, calm" was a tie broken by label order, not a reading of the end of combat. The fight-over question also returned exactly 50%, which met the old ≥50% threshold. Now invalid numbers are an error (the embeddings decide alone), and the threshold is strictly above 50%.

**Gemma 4 E2B** (`onnx-community/gemma-4-E2B-it-ONNX`, q4f16, about 3.1 GB) gives valid answers and runs at 0.45–0.9 s per scene. On TEST (`results/gemma4-e2b.json`):

| Method | DEV | TEST | Combat starts | Combat ends | Off-topic |
|---|---|---|---|---|---|
| Embeddings alone | 84% | 64% | 75% | 33% | 90% |
| Current prompt alone + fight-over | 84% | 83% | 50% | 92% | 40% |
| Current prompt + embeddings + fight-over (shipped) | 95% | 83% | 100% | 92% | 80% |
| JSON prompt (soundtrack framing), names only | 74% | 79% | 75% | 67% | 20% |
| JSON prompt with meanings | 74% | 79% | 63% | 67% | 10% |
| JSON prompt with meanings and the current soundtrack, + fight-over | 89% | 85% | 63% | 83% | 50% |

The JSON prompt is the user's suggestion: one question for both axes, framed as choosing the soundtrack, answering in JSON (prefilled up to each value in Gemma 4's own format, which free generation confirms). It does best alone once told what's playing, but misses off-topic chat, which it's never told about.

## Round 3: prompts, a 2-bit build and re-tuning the blend (2026-10-10)

Runs: `results/r3-gemma4-e2b-q4f16.json` and `results/r3-gemma4-e2b-q2f16.json` (same scenes and code as round 2; the round-2 numbers reproduced exactly, so runs are deterministic).

**Tuning by cross-validation.** The DEV set (19 scenes) is too small to choose blend settings on: 84 settings tied for best on DEV and scored anywhere from 75% to 92% on TEST. `analyse.mjs --tune` instead uses 5-fold cross-validation over all 127 scenes: it chooses the blend's weights, softening and fight-over threshold on four fifths, scores the fifth, and rotates.

| Gemma 4 E2B | Download | Per scene | Alone + fight-over (TEST) | Blend, old settings (all scenes) | Blend, tuned (cross-validated) |
|---|---|---|---|---|---|
| 4-bit (q4f16), current prompt | 3.1 GB | 0.65 s | 83% | 85% | **92%** |
| 4-bit, JSON prompt with meanings and the current soundtrack | | 0.9 s | 85% | 83% | 90% |
| 4-bit, the same plus "table talk means keep the soundtrack" | | 1.0 s | 84% | 83% | 91% |
| 2-bit (QAT mobile, q2f16), current prompt | 2.3 GB | 2.8 s | 52% | 75% | 74% |

- **The tuned blend for the current prompt** is half and half on both axes, softening 2 (square root), fight-over above 50%; every fold chose the same settings. Shipped. On TEST it gets 92%: openings 93%, setting changes 92%, tense 100%, combat 100%, combat starts 75% (100% with the old settings), combat ends 92%, off-topic 80%.
- **The off-topic line** in the JSON prompt didn't help: Gemma alone still misses most table talk; the embeddings catch it.
- **The 2-bit build** is four times slower on the M5 (WebGPU has no fast 2-bit kernels) and much less accurate; in free text it even answered "haunted manor" as a setting. Dropped. It also ships without a chat template; `--tokenizer` borrows the 4-bit build's.
- **Gemma alone or the blend?** The blend wins clearly once tuned (92% against 83–85%), so the embeddings stay.

## Decision

Keep every reasonable option and default to a strong local one. Since round 2 the LLM is Gemma 4 E2B; the rest of this section dates from round 1.
- Local scene checks always blend Gemma 3 4B with the embeddings. An "embeddings only" choice was offered at first and then removed; the embeddings alone are only a stopgap while Gemma downloads or where there's no WebGPU.
- The embeddings stay inside the blend. Gemma alone (`gonly.mjs`) gets 60% of TEST, or 62% with the fight-over question, against 79% for the blend. It catches only 13% of fights starting.
  - Asked directly "has a fight started?" (`fight-start.mjs`), it caught 2 of 15 starts: it gave "initiative, they go first and swing at the paladin" 8%. It never raised a false alarm (0 of 48).
  - So the embeddings catch fights starting and Gemma catches them ending.
- Qwen3 1.7B (70% at half Gemma's download) comes back once a re-packed copy is hosted.
- A and B are dropped: neither beat the embeddings alone by enough to justify another option.
- Models defaults to Local. Claude stays available with an API key, and runs alongside for comparison when there is one.

`experiments/e9/app-blend.mjs` runs the app's own prompt and blend code (the worker's scoring is mirrored, since the worker needs a browser). It reproduces 70% on TEST with Qwen3 1.7B, and confirms both models score every question in a single pass.

## Why Gemma called "Roll for initiative" calm (2026-10-10)

In a real session, the first scene check after "Roll for initiative" got calm from Gemma 4 E2B and combat from the embeddings. The blend was a 50/50 tie, so nothing changed until the next check, about 45 seconds late. `e9/explain.mjs` asks the app's exact question again, scores it as the app does, then asks the model to explain itself in writing:

| Transcript | Scene until now | Scored (app) | "Explain, then answer" |
|---|---|---|---|
| "Roll for initiative" | tavern, calm | calm 100% | calm: "a standard instruction for starting a game session … not that a crisis is unfolding" |
| "Roll for initiative" | tavern, tense | tense 100% | combat: "a direct instruction typically given at the start of a combat encounter" |
| "Roll for initiative / Role for initiative / Let's fight" | tavern, calm | combat 100% | combat |

- **The anchor dominates.** With a single line, the one-word answer just repeats "until now the scene was …", with complete confidence. The prompt's "keep that answer unless the transcript shows it has changed" was added to stop flip-flopping, but it also stops a lone cue from counting.
- **It misreads the phrase**: it took "roll for initiative" to mean starting the game session, yet with a tense scene before it, it knew the phrase starts combat.
- **Reasoning first helps a little**: it flipped the tense case to combat but not the calm one.
- An initiative keyword cue was added and then removed again: the classifier itself needs to get better first (DESIGN.md 7.4).

## Round 4: context, a softer anchor, and thinking time (2026-10-11)

Can Gemma 4 E2B do better with more context or more time to think? Variants (`src/eval/llm-variants.ts`):
- **brief**: a system message saying it's choosing music for a live D&D session, how scenes move between calm, tense and combat, and that table talk doesn't change the scene.
- **soft**: "The music playing now is for: X. Judge mainly from the latest lines whether the scene has changed" in place of "Keep that answer unless the transcript shows it has changed".
- **reason-160**: up to 160 tokens of written reasoning before the intensity answer, forced by starting the answer with "Reasoning:" (asked to "think briefly, then answer", it just answered). The labels are then scored after the reasoning.
- **think-256**: up to 256 tokens of Gemma 4's own thinking mode (`enable_thinking`), likewise only for intensity.

On TEST (`results/r4-test.json`, 108 scenes; one scene is about 1 point, and categories have 8–30 scenes):

| Variant | Per scene | Alone + fight-over | Blended + fight-over | Combat starts (8) | Combat ends (12) | Off-topic (10) |
|---|---|---|---|---|---|---|
| current (shipped) | 0.7 s | 83% | 92% | 75% | 92% | 80% |
| brief | 1.8 s | 75% | 83% | 38% | 92% | 90% |
| soft | 0.7 s | 85% | 90% | 75% | 92% | 70% |
| reason-160 | 2.2 s | 82% | 91% | 75% | 83% | 80% |
| think-256 | 5.4 s | 89% | 94% | 100% | 92% | 70% |
| brief + reason-160 | 3.8 s | 77% | 84% | 50% | 92% | 90% |
| brief + think-256 | 8.3 s | 80% | 86% | 50% | 92% | 80% |

- **The brief made it worse**, mostly at fights starting and fights in progress: told that table talk doesn't change the scene, it keeps the scene more often. A first draft that said "most of the time the party is… calm" also pulled openings to calm.
- **Thinking mode helped Gemma alone** (83% → 89%) but only 2 points in the blend, within noise, at 8 times the cost. Short written reasoning didn't help; it often reasoned wrongly ("the conclusion of a combat encounter … followed by a discussion about resting. Answer: combat"), answering whether there was a fight in the excerpt rather than what's happening now.
- **Gemma is close to 100% sure of nearly every answer**, right or wrong, as instruction-tuned models tend to be. So one wrong answer outweighs the embeddings.
- **The test set is too small** to tell most of these apart. Round 5 adds a much larger set.

## Round 5: a larger set, and asking about change (2026-10-11)

**A larger set.** `src/eval/large/` adds 232 scenes written by Claude and reviewed by the user (`e9/label-review.mjs`; all approved, eight labels refined from the user's notes). With TEST that's 340 scenes. The shipped setup scores 92% on TEST but **81% on the large set**: TEST flattered it. Round 4's ranking held on the large set (`results/r4-large.json`): current 81%, soft 78%, brief 75%, think-256 84% (blended, with fight-over).

**Asking about change** (`change` in `llm-variants.ts`, `results/r5.json`). Instead of "how intense is the scene?", yes/no questions chosen by the current scene, with the newest line shown apart from the earlier ones:
- calm: has a fight started? Are they in danger now?
- tense: has a fight started? Has the danger passed?
- combat: has the fight ended? Are they still in danger?
- setting: have they moved somewhere new? Only then, where?

| On the large set (232), blended + fight-over | All | Setting changes | Tense | Combat starts | Combat ends | Off-topic |
|---|---|---|---|---|---|---|
| current (shipped) | 81% | 85% | 82% | 72% | 75% | 67% |
| change | 76% | 47% | 61% | 91% | 92% | 83% |
| change, calibrated | 75% | 68% | 55% | 88% | 79% | 60% |
| **mix**: current, but P(combat) from "has a fight started / ended?" | **84%** | 85% | 82% | 84% | 79% | 67% |

- **"Has a fight started?" works**: fights starting go from 72% to 84–91%.
- **"Are they in danger?" doesn't**: as a yes/no question it misses a triggered trap, a threat in the tavern and a rooftop chase, all of which the three-way question gets right. "Have they moved?" also misses most setting changes.
- **Calibration** (dividing out the answer to a content-free "N/A" transcript, as in Calibrate Before Use) made it worse: the N/A answers aren't a fair baseline for these questions.
- **Mix** (computed offline from the saved answers) keeps the three-way question for calm against tense and the setting, and takes the chance of combat from the fight questions. Re-tuning the blend by 5-fold cross-validation over all 340 scenes chose the shipped settings for both: current 85%, mix 86%. A small gain overall, but a consistent one at fights starting, on both sets, for 0.3 s more per check.

**Where this leaves prompting.** Across rounds 4 and 5, every prompt change moved the overall score by a few points at most, and the remaining misses (fights ending, table talk) haven't moved. Gemma 4 E2B seems close to what prompting alone can get from it.

**Shipped**: the mix, with Gemma 4 E2B. The fight question and the combining rule live in `src/classify/llm-prompt.ts` (`fightQuestion`, `mixIntensity`), called by both the app (`src/llm/scene-llm.ts`) and the evaluation page (`mix` in `llm-variants.ts`). The user's priority: entering and leaving combat matter most, and tension may suffer for them.

### Gemma 4 E4B (`results/r5-e4b.json`)

The next size up (`onnx-community/gemma-4-E4B-it-ONNX`, about 6 GB to download, 12 minutes the first time) answers in 1.3 s with the current questions and 1.7 s with the mix, about twice E2B's time.

| Blended + fight-over | All 340 (shipped blend) | Large set | Combat starts | Combat ends | Tense | Setting changes |
|---|---|---|---|---|---|---|
| E2B, mix (shipped) | 86% | 84% | 84% | 79% | 82% | 85% |
| E4B, current | 80% | 77% | 91% | 79% | 76% | 57% |
| E4B, mix | 79% | 77% | 94% | 83% | 67% | 57% |

- **E4B is better at fights starting and ending**, the transitions that matter most, by 2–3 scenes in each.
- **But it hears tension everywhere**, at full confidence: a card game, a temple visit, boarding a ship. Asked why, about the card game: "The introduction of cheating … escalate[s] the situation from casual to high-stakes." So calm scenes, mostly the setting-change ones, go wrong.
- **Scaling down its "tense" probability doesn't fix it**: its answers are so certain that even dividing tense by 100 only takes the large set from 77% to 80%. Re-tuning the blend by cross-validation gives 81–82%.
- **Verdict**: not worth twice the download and the time. E2B with the mix stays.

### Table talk no longer overrules Gemma (2026-10-11)

In a real session ("An angry gang walks in." then "Where's our money? Where's our money?"), Gemma said tense twice, but the embeddings heard the second check as table talk, and an off-topic win kept the current intensity whatever Gemma said, so the change to tense never got its second agreeing check. Now table talk keeps the intensity only when Gemma also hears no change (`offtopic` in `BlendOptions`; `analyse.mjs --offtopic=`):

| Mix, blended + fight-over | All 340 | Large set | Tense (large) | Combat starts | Combat ends | Off-topic (large) |
|---|---|---|---|---|---|---|
| table talk vetoes (before) | 86% | 84% | 82% | 84% | 79% | 67% |
| only if Gemma hears no change (shipped) | **88%** | **86%** | **94%** | 84% | 79% | 67% |
| never veto | 88% | 86% | 94% | 84% | 79% | 67% |

The veto bought nothing at table talk on these sets and cost a third of the tense misses. Cross-validated tuning still picks the shipped blend weights.
