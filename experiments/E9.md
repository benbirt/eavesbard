# E9 — Local scene classifiers

**Status:** first round done offline (2026-10-10). Best: the current embedding classifier blended with a small instruction LLM, 70–74% on the held-out set against 63% for the classifier alone. Built into the app with Gemma 3 4B (DESIGN.md 7.5).

## Test sets

- **DEV** (`src/eval/scenarios.ts`, 17 scenes): the scenes the current classifier was tuned on. Used only to choose settings and blend weights.
- **TEST** (`src/eval/test-set.ts`, 108 scenes, held out): messy, Whisper-style transcript lines 15 s apart, plus typed opening descriptions. Each scene lists every acceptable setting and intensity.

| Category | Scenes | What it checks |
|---|---|---|
| opening | 30 | a typed opening description |
| setting | 24 | the setting changes during play |
| tense | 12 | danger without a fight |
| combat | 12 | a fight in progress |
| combat starts | 8 | a fight breaking out |
| combat ends | 12 | a fight just over |
| off-topic | 10 | table talk: rules, food, scheduling |

A result counts as right after the state machine's own rules (DESIGN.md 7.6): unknown or under-50%-confident results keep the current label, and an unknown opening setting becomes tavern. "Both" means setting and intensity are both right.

The harness is in `experiments/e9/`: Node, transformers.js 4.3.1 on the CPU (4 cores), importing the compiled sets from `bazel-bin`. Install it with `npm install --ignore-scripts`, then run `node <file>.mjs`.

## Results on TEST

| Method | Download | Time per check (CPU) | Setting | Intensity | Both |
|---|---|---|---|---|---|
| **L** — current: embeddings vs hand-written label descriptions | 34 MB | ms | 83% | 76% | 63% |
| **A** — vote of the 20 nearest tracks' tags | 34 MB | ms | 72% | 54% | 38% |
| **B** — zero-shot NLI, `MoritzLaurer/deberta-v3-xsmall-zeroshot-v1.1-all-33` | 87 MB | 0.1 s | 81% | 63% | 51% |
| **C** — Qwen3-1.7B (q4) | 1.4 GB* | 3 s | 81% | 74% | 61% |
| **C** — Gemma 3 4B (q4, text only) | 2.8 GB* | 7 s | 89% | 69% | 60% |
| L + B blend | 120 MB | 0.1 s | 85% | 75% | 66% |
| **L + Qwen3-1.7B blend** | 1.4 GB* | 3 s | 87% | 81% | **70%** |
| **L + Gemma 3 4B blend** | 2.8 GB* | 7 s | 92% | 81% | **74%** |

\* Browser q4f16 download for WebGPU. The CPU test used the q4 files, which are larger. On WebGPU each check should be well under the CPU times.

Blend weights were chosen on DEV and then scored once on TEST. Setting takes an even split of the two probability distributions; intensity takes 75% L and 25% LLM. L's off-topic rule is kept; its "unknown setting" rule is dropped because it costs openings.

L + Gemma 4B by category: opening 80%, setting 75%, tense 75%, combat 83%, combat starts 88%, combat ends 42%, off-topic 70%.

**Other models tried for B** (both, TEST): mobilebert-mnli 25%, distilbert-mnli 38%, nli-deberta-v3-xsmall 19%, nli-deberta-v3-small 19%.

**Other models tried for C**: SmolLM2-360M, Qwen2.5-0.5B, Qwen3-0.6B, Gemma 3 270M, Gemma 3 1B and Qwen2.5-1.5B all scored 2–31% both, near chance. Gemma 3 1B degrades badly when quantised for the CPU (q4 or 8-bit): it answers "Tavern" to "deep underground caverns", while at full precision it answers "Dungeon".

## How C works

- There is one forward pass per axis and no free generation.
- The prompt has the transcript (the last 150 words for the setting, 60 for the intensity) and the current scene ("keep that answer unless the transcript shows it has changed"). It lists the labels with one-line meanings and ends with "Answer:".
- The answer is read from the next-token probabilities of each label, adding the " dungeon" and " Dungeon" forms.
- Telling the model the current scene took Qwen3-1.7B from 47% to 61%.
- Reading the first answer token on its own, without prefilling "Answer:", gave near-random results: the models want to begin "From the given options…".

## Findings

- The approaches fail in different places. L is strong on combat and combat starting. The LLMs are strong on settings and tense scenes but slow to call combat. Blending fixes most of both.
- Combat ending is the weakest category for every method (25–58%).
- No method uses anything written per track, so the track index can be regenerated without anyone in the loop. L and B use a handful of one-line label definitions.
- Not compared with Claude Haiku on TEST: no API key was available. That reference number is still missing.

## In the browser

Tested in headless Chromium with SwiftShader (a CPU standing in for the GPU) through the app's own worker (`src/llm/llm-worker.ts`):
- **Gemma 3 4B** downloads, loads and answers. "Deep underground caverns" gives dungeon at over 99.9%. It took 74 s to download and prepare, and 293 s for the answer on SwiftShader; a real GPU is far faster.
- **SwiftShader has no 16-bit floats** (`shader-f16`), so the q4f16 files can't run on it. The worker checks for `shader-f16` and falls back to the q4 files (32-bit activations; about 3.2 GB for Gemma) on GPUs without it.
- **Qwen3 1.7B doesn't load:** onnx-community's q4f16 build is a single 1.4 GB file, and ONNX Runtime Web fails with `std::bad_alloc` creating the session. Gemma's builds keep the weights in separate `.onnx_data` files, which load. Re-saving Qwen's file that way (`experiments/e9/repack.py`) and serving the copy locally, the session loads and gets as far as SwiftShader's missing 16-bit floats. So Qwen3 1.7B would work from a hosted re-packed copy, for example a Hugging Face repo of ours, with `transformers.js_config.use_external_data_format` set in its `config.json`.

## Follow-up: fights not ending (real session, 2026-10-10)

In a real session with Gemma on a laptop GPU (about 1 s per check), "Roll for initiative" started combat, but "you killed the last enemy" and "Combat over" didn't end it:
- The embeddings read both as combat: they can't read negation.
- Gemma said calm both times, but had only 25% of the intensity vote.

Both checks are now in the DEV set. On the cached answers (`mix2.mjs`, `int-variants.mjs`):

| Change | TEST both | Combat ends |
|---|---|---|
| Blend as shipped | 74% | 42% |
| Gemma's answers softened (temperature 3) | 78% | 42% |
| Gemma not told the current scene, more weight in combat | 78% | 50% |
| Gemma told "before these lines the scene was …" | 77% | 0–33% |
| More LLM weight while in combat (without softening) | 73% | 33% |

Gemma is anchored by "keep that answer unless the transcript shows it has changed": mid-fight it calls looting and healing combat at 100%.

A direct question works better. While in combat, Gemma is also asked "is the fight still going on right now?" (ongoing or over; `fight-over.mjs`). Over all 26 scenes that start in combat:
- It never said over for a fight still going (0 of 9).
- It caught 7 of 17 endings, including both real ones (98% and 100%).
- The answers are almost always 0% or 100%, so the threshold hardly matters.

With softening and the fight-over question, TEST is 79% (combat ends 50%). Both are in the app.

## Decision

Keep every reasonable option and default to a strong local one:
- Setup → Local scene model offers embeddings only and embeddings + Gemma 3 4B. Gemma is the default where there's WebGPU and the browser reports at least 8 GB of memory. Otherwise the default is embeddings only: a 3 GB model alongside Whisper is too much for a phone.
- Qwen3 1.7B (70% at half Gemma's download) comes back once a re-packed copy is hosted.
- A and B are dropped: neither beat the embeddings alone by enough to justify another option.
- Models defaults to Local. Claude stays available with an API key, and runs alongside for comparison when there is one.

`experiments/e9/app-blend.mjs` runs the app's own prompt and blend code (the worker's scoring is mirrored, since the worker needs a browser). It reproduces 70% on TEST with Qwen3 1.7B, and confirms both models score every question in a single pass.
